## Risks and tradeoffs

- Vendored Warp source is AGPL-3.0. Shipping a Warp-derived companion binary or integrated launcher requires preserving notices and making corresponding source available under compatible terms.
- The Python OBus SPA should not attempt to embed Warp Rust code; the process/MCP boundary is intentionally safer and more maintainable.
- Execution-scope confirmation may alter route UX for remote providers. This is intentional: explicit consent is necessary when prompt content leaves the local runtime.
- Do not “fix” the primary `dist/OBus.exe` lock by terminating unrelated user instances. Build to an isolated output directory until ownership of running processes is confirmed.
- Existing untracked files and automated status-report changes are outside this plan; do not delete, overwrite, stage, or commit them without explicit operator direction.

## Completion criteria

- Receipt redaction tests cover bare keys, Bearer, Basic authorization, header values, PEM, persistence, detail, and export.
- Warp launch resolves only the expected local `warp-tui-oss` binary beneath an approved source root.
- `git submodule status --cached` succeeds without missing mappings.
- Route plan, run response, receipt, and UI accurately distinguish preview/local/remote execution.
- All visual toggles are keyboard reachable.
- Offline integrations show bounded, truthful recovery guidance.
- Full tests, JavaScript syntax check, packaged artifact smoke test, and visible UI capture pass.
